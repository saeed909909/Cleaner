The problem with dense models

In the transformer from Chapter 9, every token passes through every weight in every layer. A 70-billion-parameter model does about 70 billion multiply-adds for every single token it reads or writes. Models built this way are called dense.

That's wasteful. When the model is working on a line of Python code, it probably doesn't need the parts of itself that know about medieval poetry. Yet a dense model consults everything, every time. Making it twice as knowledgeable means making every token twice as expensive.

The idea: specialists and a receptionist

A Mixture of Experts (MoE) model replaces the single feed-forward network in each transformer block with many smaller feed-forward networks side by side, called experts, plus a tiny network called the router (or gating network). For each token, the router picks just a few experts to use. The rest sit idle for that token.

{{fig:moe_block|Inside one MoE layer. The router scores every expert for this token and sends it to the top two. Their outputs are combined, weighted by the router's scores. The other experts do no work for this token.}}
Analogy

A hospital. In a dense model, every patient is examined by every doctor in the building: thorough, but absurdly slow. In an MoE hospital, a receptionist at the entrance (the router) looks at each patient and sends them to the two most suitable specialists. The hospital can employ hundreds of specialists, but each patient only takes up two doctors' time.

How routing works

  1. The token's current numbers (from the residual stream) go into the router, which is just a small table of weights.
  2. The router outputs a score for each expert, and a softmax turns the scores into shares.
  3. The top k experts are chosen, typically 1, 2 or 8, depending on the model. This is called top-k routing.
  4. The token is processed by just those experts, and their outputs are added together, weighted by the router's shares.

The router is trained along with everything else by backpropagation. Nobody tells it which expert is for what; it learns whatever routing makes the predictions best.

Total versus active parameters

MoE splits the meaning of “model size” in two, and this is the single most important thing to understand when reading about these models:

  • Total parameters: every weight in the model, including all the experts. This decides how much memory you need to hold it, and roughly how much it can know.
  • Active parameters: the weights actually used for one token. This decides how much computation each token costs, and so how fast it runs.

Good to know: reading the names

MoE model names often encode the sizes. “8x7B” means eight experts of roughly a 7B model each, although the total is less than 8 × 7 = 56B, because the attention layers and embeddings are shared, not copied. A name like “30B-A3B” means 30 billion total parameters with 3 billion Active per token.

A common misunderstanding

The word “expert” suggests a maths expert, a history expert and a coding expert, like separate chatbots inside one. That is not how it works.

  • The experts are not whole models. Each is one feed-forward network inside one layer. A model with 32 layers and 8 experts per layer has 256 expert networks in total, and every layer routes independently.
  • Routing happens per token, not per question. Within a single sentence, consecutive tokens are often sent to different experts.
  • Specialisation is real but rarely matches human subjects. When researchers inspect routers, they often find experts that prefer things like punctuation, numbers, particular word pieces, or code syntax, rather than “history”.

Keeping the experts busy: load balancing

Left alone, routers tend to fall into a lazy habit: a few experts get slightly better early on, so the router sends them more tokens, so they improve more, so they get even more tokens. Soon most experts sit idle, wasting their parameters. This is called routing collapse.

To prevent it, training adds load balancing: usually a small extra penalty in the loss (an auxiliary loss) whenever the tokens are spread too unevenly, or an adjustment that nudges the router towards under-used experts. Some designs also include shared experts that every token always uses, to handle common knowledge, so the routed experts can specialise.

Analogy

If the receptionist sends every patient to the same famous doctor, the queue becomes enormous and the other doctors forget their training. A good hospital manager watches the queues and steers patients to doctors with spare time, as long as they're suitable.

There is also a hardware limit. Each expert can only handle so many tokens per batch, called its capacity. If too many tokens choose the same expert, some may be passed on without that expert's processing (token dropping). Balancing keeps this rare.

The costs of MoE

  • Memory. Every expert must be loaded, even though few are used per token. A 47B-total MoE needs memory for 47B parameters while running at the speed of a 13B one. For home users with limited graphics memory, this is often the deciding factor.
  • Communication. In data centres, experts are spread across many GPUs (expert parallelism), so tokens must be shuttled between chips constantly. Fast connections between chips matter even more than usual (Chapter 14).
  • Training is fiddlier. Routing collapse and instability need careful handling.
  • Per-parameter efficiency. An MoE model is usually somewhat less capable than a dense model with the same total parameters, but far more capable than a dense model with the same active parameters. It wins on cost, not on size.

A short history

The idea of a mixture of experts with a gating network dates from 1991, decades before deep learning. In 2017 Noam Shazeer and colleagues at Google built a “sparsely-gated” MoE layer with thousands of experts inside a language model. Google's Switch Transformer (2021) simplified routing to a single expert per token and scaled past a trillion parameters. Mixtral (2023) made a high-quality open MoE model widely available, and DeepSeek's models (2024–2025) showed how far very fine-grained experts could go. MoE models are often called sparse models, because only a small part of the network is active at any moment.

In plain words

An MoE model has many alternative feed-forward networks in each layer and a router that picks a few per token. You get the knowledge capacity of all the experts for roughly the running cost of the few you use. The catch: you still need memory for all of them.
